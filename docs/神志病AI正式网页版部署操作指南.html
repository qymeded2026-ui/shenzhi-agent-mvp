1. 你最终会得到什么

完成部署后，你会有两个线上地址：

地址类型 示例 用途
前端网址 https://shenzhi-agent.vercel.app 发给别人访问。用户看到的网页 UI、聊天界面、评分面板都在这里。
后端网址 https://shenzhi-agent-api.onrender.com 前端背后调用的 API 服务。负责病例、问诊、评分、PDF 导出、DeepSeek 调用。
一句话理解：前端是“网页外壳和操作界面”，后端是“系统大脑和数据接口”。别人只需要打开前端网址，前端会自动请求后端。

3.3 不要提交到 GitHub 的内容

这些内容不能上传，尤其是 API Key：

  • .venv/：本地 Python 虚拟环境。
  • frontend/node_modules/：本地前端依赖。

  • reports/：本地导出的报告。

项目中的 .gitignore 已经排除了这些内容，但上传前仍建议用 git status 看一眼。

6. 部署后端到 Render

后端负责所有核心功能：病例读取、问诊对话、评分、PDF 导出、模型调用。因此后端必须先部署成功，前端才能正确连接。

6.1 创建 Web Service

登录 Render

进入 Render 控制台，点击 New +，选择 Web Service。

连接 GitHub 仓库

选择你刚刚上传的项目仓库。如果第一次使用，需要授权 Render 读取 GitHub。

填写服务配置

配置项 填写内容
Name shenzhi-agent-api
Root Directory 留空，表示项目根目录
Runtime Python
Branch main
Build Command pip install -r requirements.txt
Start Command python api_server.py
Health Check Path /api/health

6.2 配置环境变量

在 Render 的 Environment 页面添加：

Key Value
DEEPSEEK_API_KEY 你的 DeepSeek API Key。不要写进代码，不要上传 GitHub。
SHENZHI_RUNTIME_DIR /opt/render/project/src/runtime
Render 会自动提供 PORT 环境变量。当前后端代码已经支持它：线上会监听 0.0.0.0:$PORT，本地仍默认监听 127.0.0.1:8765。

6.3 部署并检查

  1. 点击 Deploy Web Service。
  2. 等待日志里出现类似 Shenzhi API listening。
  3. 打开后端健康检查地址：
https://你的后端域名.onrender.com/api/health

正常返回：

{"status": "ok"}

6.4 关于持久化数据

当前问诊历史会写到运行目录中的 SQLite 数据库。Render 如果没有挂持久化磁盘，服务重启或重新部署后，运行时数据可能丢失。

演示阶段可以先不挂磁盘；如果要长期给别人用，建议在 Render 给服务添加 Persistent Disk，然后把 SHENZHI_RUNTIME_DIR 设置为磁盘挂载目录。

7. 部署前端到 Vercel

前端是用户真正访问的网址。它不保存 DeepSeek API Key，只通过环境变量知道后端在哪。

7.1 导入项目

登录 Vercel

进入 Vercel 控制台，点击 Add New Project 或 Import Project。

选择 GitHub 仓库

选择同一个 shenzhi_agent_mvp 仓库。

填写构建配置

配置项 填写内容
Framework Preset Vite
Root Directory frontend
Build Command pnpm build
Output Directory dist

7.2 设置前端环境变量

在 Vercel 的 Environment Variables 里添加：

VITE_API_BASE_URL=https://你的后端域名.onrender.com

注意：

  • 不要在末尾加 /，例如不要写成 https://xxx.onrender.com/。
  • 改了这个环境变量后，必须重新部署前端，因为 Vite 会在构建时写入变量。

7.3 发布并访问

  1. 点击 Deploy。
  2. 构建成功后，Vercel 会给你一个前端网址。
  3. 打开前端网址，确认能看到登录/工作台界面。
如果页面能打开但问诊失败：多数是 VITE_API_BASE_URL 配错、后端没启动、后端 API Key 没配，或者前端改环境变量后没有重新部署。

9. 上线后的完整验证流程

部署完成后不要只看首页，要按下面清单逐项验证。

9.1 后端验证

  • 打开 /api/health，返回 {"status":"ok"}。
  • Render 日志没有持续报错。
  • 环境变量里已经填入 DEEPSEEK_API_KEY。

9.2 前端验证

  • 前端网址能打开。
  • 登录界面/工作台 UI 显示正常。
  • 能进入问诊页面。
  • 左侧历史记录、中间对话、右侧评分面板显示正常。

9.3 功能验证

功能 验证动作 通过标准
新建问诊 点击新建会话或进入默认会话。 能看到病例标题和聊天输入框。
患者回复 发送“你最近主要哪里不舒服？” 患者 Agent 返回符合病例的自然回答。
评分反馈 连续问 2-3 个问题。 本轮评分和右侧评分详情能更新。
督导反馈 在右侧督导区域提问。 能给出下一步问诊建议。
PDF 导出 点击导出问诊记录。 下载 PDF，内容包含本轮全部问诊记录。

9.4 Network 检查

打开浏览器开发者工具，进入 Network。刷新页面后查看请求：

  • /api/chats 应该请求到 Render 后端域名。
  • 如果请求跑到 Vercel/Netlify 自己的域名，说明 VITE_API_BASE_URL 没生效。
  • 如果接口返回 500，去 Render Logs 看后端错误。

10. 后续更新怎么发布

后续修改 UI、评分逻辑、患者 Agent 提示词或 PDF 导出后，按下面流程发布。

cd /Users/qymeded/Desktop/shenzhi_agent_mvp
git status
git add .
git commit -m "Describe your update"
git push

推送后：

  • Vercel 通常会自动重新部署前端。
  • Render 如果开启 Auto Deploy，也会自动重新部署后端。
  • 如果只改了后端，前端不一定需要重新部署。
  • 如果改了 VITE_API_BASE_URL，必须重新部署前端。
建议发布节奏：每次只改一个主题，例如“登录 UI 优化”“评分逻辑优化”“PDF 导出优化”。这样线上出问题时容易回退。

11. 常见问题排查

问题 1：前端页面打开了，但发送消息失败。

先检查后端健康接口是否正常，再检查 Vercel 的 VITE_API_BASE_URL 是否是 Render 后端域名。改完环境变量后要重新部署前端。

问题 2：Render 后端部署失败。

看 Render Logs。重点检查 Build Command 是否是 pip install -r requirements.txt，Start Command 是否是 python api_server.py。

问题 3：后端显示启动了，但健康检查打不开。

通常是服务没有监听平台端口。当前代码已经支持 PORT，如果仍失败，确认线上运行的是最新代码，并检查日志里的监听地址。

问题 4：AI 不回复或一直报错。

检查 DEEPSEEK_API_KEY 是否填在 Render 后端环境变量中，而不是 Vercel 前端。还要检查 DeepSeek 账号额度和服务状态。

问题 5：PDF 导出失败。

确认后端服务正常，当前会话确实有问诊记录。Network 里应看到类似 /api/chats/xxx/export 的请求，响应类型应该是 application/pdf。

问题 6：历史记录重启后消失。

这是没有配置持久化磁盘导致的。演示阶段可以接受；长期使用需要 Render Persistent Disk 或外部数据库。

问题 7：Vercel 构建失败，提示 pnpm 找不到。

在 Vercel 构建配置里保持 pnpm build。如果平台没有自动识别，可改成 corepack enable && pnpm install && pnpm build，或在项目中补充平台配置。

问题 8：浏览器提示 CORS。

当前后端默认允许跨域。如果后续改了 CORS 限制，需要把你的 Vercel/Netlify 前端域名加入允许列表。

12. 公开分享前的安全提醒

重要：当前登录界面主要是 UI 状态，不是真正的后端账号鉴权。只要别人知道前端网址，就可能使用后端接口并消耗你的 DeepSeek API Key。

正式公开分享前，建议至少做一种保护：

  • 给后端加真实登录鉴权。
  • 给演示版本加访问密码。
  • 限制 CORS，只允许指定前端域名访问。
  • 设置请求频率限制，避免多人同时大量调用。
  • 演示阶段只把链接发给小范围测试用户。

推荐的正式上线顺序

  1. 先部署后端，并确认 /api/health 正常。
  2. 再部署前端，并设置 VITE_API_BASE_URL。
  3. 自己完整走一遍问诊和 PDF 导出。
  4. 发给 1-2 个熟人测试。
  5. 确认稳定后再扩大分享范围。
